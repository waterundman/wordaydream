### 3.1 全矩阵 7 个失败的定性（webkit ×6 + firefox ×1，非本轮回归）

四条证据链：

1. **基线口径全绿**：chromium project 24/24 通过。v1.6.2 记录的「E2E 20/20」本就是 chromium 口径；`e2e/web.spec.ts` 仍为 20 个用例且**本轮零改动**（`git diff -- e2e/ playwright.config.ts` 为空）。
2. **失败用例的实现文件零改动**：T04/T05（CSV/JSON 下载）、T09（发音）对应的 web 侧文件（`speakText.ts`、导出链）**未被 Wave 1 触及**；唯一 TTS 改动在原生侧 `TextToSpeechService.ets`，不参与浏览器 e2e。
3. **失败形态是浏览器能力差异**：webkit 的 `Test timeout 30000ms exceeded`（页面快照停在主页，即加载极慢）、`offline-install` 的 SW/preview、T04/T05 的下载 API、T09 的 speechSynthesis —— 全是 webkit on Windows 的已知弱项。
4. **既往记录佐证**：`docs/ci-audit-2026-09-05.md:135` 记录 webkit 曾全过，但当时**只有 4 个用例**；v1.6.x 新增的 T04–T20 **从未在 webkit/firefox 上验证过** —— 这是矩阵覆盖盲区，不是本轮引入的破坏。

> **结论**：7 个失败 = 「后加用例 × 未验证过的浏览器」的既有盲区首次暴露。归入待办（修 webkit 兼容或收缩矩阵），**不阻塞本轮收口**；但必须在下一版决策，不能持续默认红。

## 4. 关键结论：日志脱敏未断链（新增独立证据）

`scripts/harmony/assertion-keywords.mjs` 声明硬约束「keyword 必须与运行时日志源**逐字一致**」。本轮做了日志脱敏（改动 `Index.ets` / `HarmonyBridge.ets` / `EntryAbility.ets`），二者**存在耦合风险**，而运行时验证未执行。

**故补做静态核验**（不需要模拟器）：逐条 grep 断言关键词在日志源中的存在性。

| 断言 | 关键词 | 命中位置 |
|---|---|---|
| A1 | `seedDebugCards done` | `entryability/EntryAbility.ets` |
| A2 | `Page begin` | `pages/Index.ets` |
| A3 | `Web content ready` | `bridge/HarmonyBridge.ets` |
| A4 | `getAllCards done: count=` | `useMemoryStore.ts` + `bridge/HarmonyBridge.ets` |
| A5 | `Web launch handler ready: generation=` | `bridge/HarmonyBridge.ets` |
| A6 | `dispatching query=action=openCard` | `entryability/EntryAbility.ets` |
| A7 | `[harmonyLaunch] openCard` | `domain/harmonyLaunch.ts` + `pages/Index.ets` |

**结果 7/7 逐字命中** ✅

> **口径（不得放大）**：这证明的是「断言关键词 ↔ 日志源」的**静态一致性**，即脱敏没有删改受保护的字符串。
> 它**不能**替代 `verify:harmony-runtime` —— 后者验证的是日志在真机/模拟器上**实际产出**。
