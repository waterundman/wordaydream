## 3. 已核实的缺口（本轮 grep / 校验发现，非推测）

### P0-1 例句层缺失，且存在死数据

精确统计（`python` 逐条计数）：

| 文件 | 词条数 | 有 `example` | 有 `exampleTranslation` |
|---|---|---|---|
| `en/a1..b2` | 4070 | **0** | **0** |
| `de/a1` | 645 | 645 | 645 |
| `de/a2..b2` | 3366 | **0** | **0** |

即 **7436 个词条无例句**，且唯一的 645 条德语例句是**死数据**：

- `WordlistEntry` 接口（`src/data/wordlists/index.ts`）**未声明** `example` / `exampleTranslation`
- `src/` 内对词表 `example` 字段**零引用**（仅 `prompts.ts` 中 `example` 一词指 prompt few-shot 样例，与此无关）
- `verify-wordlists.mjs` 对 `example` **无校验规则**

> 这意味着：`de/a1.json` 携带的 645 条例句既不被类型系统承认，也不被任何代码消费，也无法被契约校验保护 —— 一旦生成脚本重跑就会静默丢失。

### P0-2 SPEC 数据契约已漂移未回填

SPEC §4.1 / §16.2 声明的 `WordlistEntry` 字段集为 `{lemma, pos, translation, cefr, priority, topic}`，而 v1.6.0 实际实现已扩展为 `+ frequency + semanticConflicts`；SPEC §16.2 的示例 JSON 仍写 `"total": 80`。契约文档与实际数据不一致，后续版本若以 SPEC 为准会造成误判。

### P1-1 `topic` 粒度在 B1/B2 仍偏粗

`topic` 落到 `general` 的比例：A1 **12%** / A2 30% / B1 41% / B2 **47%**。低等级语义域词稀疏 + 上游包分类粒度粗是主因。取词队列以 topic 聚簇，`general` 占比过高会削弱「同批 targetWords 同主题、文本语义连贯」的设计意图。

### P1-2 同形异义共享 progress 状态

progress 以 `${language}:${lemma.toLowerCase()}` 为键，`de/a1` 的 11 处同形异义词（如 `sein` 动词「是」/ 限定词「他的」、`Morgen`「早晨」/「明天」）**共享同一掌握状态**。学习者掌握了其中一个义项，另一个义项也被判为已掌握。

### P2-1 词频与 CEFR 未逐词人工校对

分级与词频来自上游语料，未逐词人工复核（已在 CHANGELOG 诚实声明）。

## 4. 主推方向 P0：例句层（example layer）

**目标**：让每个词条带一条**真实、可核验**的例句 + 中文译文，并把它接入 schema 契约、校验器与 UI 消费方，形成「数据 → 契约 → 消费」完整闭环。

### 4.1 语料源（关键约束：不接受手工编造）

v1.6.0 已确立原则：**不手工编造 4000+ 条例句**（会产生错误示范效果）。本版本候选路径：

1. **优先**：寻找带例句的 MIT/CC-BY 开源语料（如 Tatoeba 多语句对、开源学习者词典 dump），按 `lemma` 匹配抽取真实句子，保留出处
2. **降级**：若外部语料不可得（沙箱网络对 GitHub 直连/代理历史多次不可达），则**不写入任何例句**，改为交付「契约 + UI 消费方就绪 + 校验规则」，并把缺口留给有语料的一方 —— 宁可空，不可编

### 4.2 Schema 契约同步

- `WordlistEntry` 接口新增可选字段 `example?: string` / `exampleTranslation?: string`
- `verify-wordlists.mjs` 新增规则：字段存在时须非空、`example` 须包含该词条 `lemma` 的屈折或原形出现（弱校验），`exampleTranslation` 与 `example` **同时存在或同时缺失**（避免半截数据）
- 回填 SPEC §4.1 / §16.2：字段集补 `frequency` / `semanticConflicts` / `example` / `exampleTranslation`，示例 JSON 的 `total` 改用真实值口径

### 4.3 UI 消费方（让例句可见）

| 消费方 | 现状 | 本版本改动 |
|---|---|---|
| 词表浏览页（`WordlistPage`） | 仅显示 lemma + 释义 | 展开行显示例句 + 译文（无例句则不渲染该行，向后兼容） |
| 答题面板（`InlineAnswerPanel`） | 显示释义 | 释义下方追加例句（存在时），作为语境强化 |
| 导出（词表 JSON / CSV） | 已含释义 | 例句字段随导出（保持 roundtrip 兼容：新列可选） |

**0 breaking change 约束**：字段全可选、UI 全按「存在才渲染」处理，旧词表（无例句）行为完全不变。

### 4.4 工期与沙箱可执行性

- 契约 + 校验规则 + UI 消费方：**100% 沙箱可执行**，约 1.5 天
- 例句语料获取与写入：依赖外部数据源可达性，约 0.5-1 天
- 整体：**2-3 天**，沙箱 95%

## 5. 次推方向

### 5.1 P1 `topic` 粒度收敛
扩充人工主题表（v1.6.0 已建 ~700 词 / 30 域），目标把 B1/B2 的 `general` 占比压到 30% 以下；`general` 词条按 pos 归入 `<pos>_general` 以至少保留词性维度。

### 5.2 P1 同形异义消歧（sense key）
为德语同形异义词引入 `senseId`（如 `sein#verb` / `sein#det`），progress 键从 `language:lemma` 扩展到 `language:lemma#senseId`（缺省时退回 lemma 兼容旧数据）。**注意**：这是 progress schema 变更，需 persist migration，属中等风险 —— 建议独立 Stage 并在有德语用户反馈后再决策。

### 5.3 P0（低成本）SPEC 回填
§3 P0-2 的契约漂移，纯文档工作，0.1 天，建议随本版本一并结清，避免后续版本以过期 SPEC 为准。

## 10. 风险与缓解

### 10.1 风险：例句语料不可达（高概率）
- 影响：Contract 46 无法交付，例句层只剩契约与 UI 空跑
- 缓解：Contract 46 显式 NOT DELIVERED，**不以编造数据凑数**；契约 + UI 消费方仍可 100% 沙箱完成，下一版本语料到位即插即用

### 10.2 风险：例句与 `lemma` 不匹配（数据质量）
- 影响：例句不含该词，示范错误
- 缓解：校验器强制 `example` 含 lemma 弱匹配；不通过则不写入该条

### 10.3 风险：Bundle 体积二次膨胀
- 影响：HAP 已因词表 +991 KB（4,765,139 B），再叠加 7000+ 例句会显著增大
- 缓解：例句仅随词表按需加载（动态 import，不进首屏）；必要时对 `example` 单独分包或改为「当前等级 + 下一等级」预取；构建后实测 HAP 体积并记录

### 10.4 风险：UI 消费方引入回归
- 影响：词表页 / 答题面板是既有高流量界面
- 缓解：字段全可选 + 「存在才渲染」，旧词表路径零改动；新增渲染用例锁定「无例句不渲染」分支

### 10.5 风险：sense key migration 破坏既有进度
- 影响：德语同形词 progress 键变更可能丢状态
- 缓解：本版本**不做**，仅记录方向；若做，必须提供旧键回退读取与 persist migration 测试
