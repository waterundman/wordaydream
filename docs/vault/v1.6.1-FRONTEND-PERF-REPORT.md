## 5. 深度记录：四个关键结论

### 5.1 `React.lazy` 首次渲染**必定挂起一次**（本轮最重要的发现）

E2E T17 用页面内 MutationObserver 探针（`appearances` / `visibleMs` / `stillPresent` 三段计数）取得硬数据：

```json
{ "appearances": 1, "visibleMs": 54, "stillPresent": false }
```

而同一用例断言「chunk 请求时刻 **≤** 点击时刻」**已通过** —— 即 **chunk 确实已预取完成**，但加载态仍闪了 1 次 / 约 54 ms。

**根因**：`React.lazy` 首次渲染时才调用工厂，拿到的是**崭新的 `import()` promise**（不是已落定的那个），于是首次渲染必然 `throw` 挂起一次。预取只能让这次 `import()` **瞬间**落定（54 ms 而非数百 ms），**不能消除挂起**。

**处置**：正常动效下这 54 ms 被墨迹覆盖层遮住，但 `prefers-reduced-motion` 用户没有覆盖层、会直接看到 → 判定为**必须修实现，不能放宽断言**。新增 `createRouteComponent(loader)`：

| 记录状态 | `React.lazy` | `createRouteComponent` |
|---|---|---|
| resolved | 仍挂起一次（首次） | **同步渲染真实组件** |
| pending | `throw promise` | `throw promise`（语义不变） |
| rejected | `throw error` | `throw error`（交给 `ErrorBoundary`） |

加载记录**按 loader 函数身份索引**，使预取路径与渲染路径共享同一条记录 —— 这是「预取完成 ⇒ 首渲染同步」成立的前提。两条路径对 `rejected` 的处理故意不同：渲染路径不替换（否则无限重试），预取路径换新记录（用户尚未导航，重试安全）。

### 5.3 View Transitions API：探针完成但**不采纳**（不是不支持）

内核取证：HarmonyOS 6.0（本项目目标 API 22）ArkWeb 默认 **M132**（可选 M114），View Transitions 自 Chrome 111 提供 → **M114/M132 都满足**。

否决理由是**设计收益为负**：
1. 现有 `InkWipeTransition` 在 cover 阶段以 `transform: scaleX(1)` **全屏遮挡**内容切换（`onCovered` 才 `setAppMode`），换页本就不可见 → VT 的跨状态快照/交叉淡入作用面与之**完全重叠**，无可见收益
2. 若改用 VT 取代墨迹转场 = 把品牌化转场换成通用交叉淡入，属**产品降级**
3. 若两者叠加，需把换页改成 `document.startViewTransition(async () => …)` 并 **await 懒加载 chunk**，与 `React.lazy` + `Suspense` 结构直接冲突，复杂度与回退风险不成比例
4. Web 侧仍需特性检测（Firefox same-document VT 落地较晚），收益进一步摊薄

### 5.4 `will-change` 审计的两条纪律与收益边界

**判据**：① 声明的属性必须真在该元素上变化（撒谎 = 噪声 + 误导读者）；② 元素数量是否随数据规模增长（永久 hint = 永久合成层，O(N数据) 不可接受）。

- **审计面修正**：SPEC 写的「14 文件」快照含 `src/App.css`（Stage 3 已删）。实际 = **13 个 .css 的 19 条规则 + 1 处 TS 内联 = 20 站点 / 14 文件**
- **9 处属性收敛**（`transform, opacity` → `transform`）：这些块的 transition 只列 `transform`，`opacity` 从未变化
- **5 处整条删除**：元素数随数据增长且动画只是「数据变化时的一次性过渡」（逐词高亮、逐天柱、逐分布桶、逐课进度条、逐行进度条）→ 改为依赖浏览器在过渡真正开始时的自动提升
- **6 处判定保留**：无限动画 / O(1) 入场揭示 / JS 真实改写的内联声明（`useCursorGlow` 在 `mousemove` 里确实改写 transform 与 opacity）
- **收益的诚实边界**：本环境**无法读取 compositor 层内存 / 合成耗时**。9 处是**语义与维护性**收敛 —— 两种写法都提升同一合成层，**无度量差异**，不应记作性能优化；5 处删除的收益是「合成层数量从 O(N数据) 降到 0」，属**原理推算而非实测**，残余风险 = 这些元素过渡的起始帧可能多一次提升动作
- **未做（有意非目标）**：没有为入场类元素引入 `transitionend` → `.settled` → `will-change: auto` 的释放管线（这些站点是 O(1)，收益不抵复杂度）

### 7.3 `versionCode` 在 1.x 线**没有机器校验**（重要提醒）

`check-version-alignment.mjs` 的线性公式 `1000000 + (minor - 3) * 5 + patch` **只对 harmony `major === 0` 成立**：

| harmony | 公式给值 | 实际值 |
|---|---|---|
| 0.6.0 | 1000015 | 1000015 ✅ |
| 1.6.0 | 1000015 ❌ | **1000065** |

脚本在 `major !== 0` 时**返回 `null` 并跳过校验**，所以「PASS」的真实含义是**「versionCode 未被校验」**。1.x 线实际节奏为**每版 +5**（0.5.0→1000010 … 1.6.0→1000065），故 `1.6.1 → 1000070`。已列为 v1.6.2 候选改进项。
