## 3. 本轮修复的 3 个脚本缺陷 (seed-and-verify.mjs)

1. **A4 关键词漂移**: 旧 `getAllCards=` 匹配的是 v0.x 日志格式 `getAllCards=0` (CURRENT_STATUS §API22 运行证据仍可见); v1.5.0 实机格式为 `getAllCards done: count=N` (HarmonyBridge.ets:700)。已改。
2. **A5 语义错位**: `queued` 在 seed (debugSeed) 阶段结构性不可能出现 —— EntryAbility.handleLaunchWant 对 `action=debugSeed` 原生拦截后直接 return, 不进 HarmonyBridge FIFO (EntryAbility.ets:183-185)。改为验证 seed 阶段真实存在且同属派发链路的 `Web launch handler ready: generation=` (notifyWebReady 就绪握手); `queued` 由 openCard 阶段 (A6 证据窗口) 实际覆盖。
3. **openCard 命令被设备 shell 拆断**: query `action=openCard&cardId=...` 含 `&`, hdc shell 拼接后由设备端 /bin/sh 解析, 裸 `&` 被当后台符 → `"/bin/sh: -b: inaccessible or not found"`。已给 query 套双引号。
4. (新增步骤) **`bm clean -d`**: 见下节, R-1 恢复契约要求验证从干净数据出发。

脚本单测 20/20 通过 (`scripts/harmony/seed-and-verify.test.mjs`, 未钉死的关键词变更不破坏契约); oxlint 0w/0e。

## 4. A7 根因分析链 (本轮核心发现)

**现象**: 干净安装 + seed 5 张到期卡 (3 en + 2 de, due=now-1h) 后派发 openCard, web 始终停留首页, toast `暂无到期复习卡片` (useToastStore 3s 生命周期, +0.8s dumpLayout 两次抓到现行), web 域层三个日志点 (located/fallback/keep-session, src/domain/harmonyLaunch.ts:93/107/113) 全未命中。

**排除项** (逐一实机/代码验证):
- 原生 FIFO 链完好: queued → dispatched remaining=0, runJavaScript resolve (handler 存在且被调用);
- web 侧校验无分歧: `LAUNCH_QUERY_REGEX` 与 `validateCardId` 均接受 `debug-seed-1`;
- launchQueue 无 stall: localStorage 为空时 onRehydrateStorage 走 getAllCards 分支, finally 必 settle;
- seed 卡字段全合法: objectiveDifficulty=3, status='review', language en/de, bridgeToMemoryCard 不会丢弃;
- bm clean 生效: streak 重置为"尚未开始连续学习"; localStorage 空 → R-1 恢复真实触发 (A4 count=5 即证)。

**根因定位**: 唯一剩余断点在 web 侧恢复 promise 链 (useMemoryStore.ts:569-593):
`bridge.getAllCards()` native 侧确认返回 5 条记录后, `.then` 链未产生 `setState({cards})` 效果 —— openCard 时 `getDueCards(lang)=0`。两个嫌疑 (外部不可分辨, 需插桩重建 HAP 判别):
- (a) **ArkWeb async JSProxy 数组返回以 JSON string 到达 web**: `for (const bridgeCard of cards)` 逐字符迭代, bridgeToMemoryCard 全部返回 null → `newCards.size===0` 静默跳过 (useMemoryStore.ts:580);
- (b) promise 跨桥 reject, 被 `.catch(() => {})` 吞掉 (useMemoryStore.ts:588)。

**暴露的流程缺口**: R-1 恢复 (getAllCards → setState) 自 v0.2.0-harmony Stage 3 落地以来从未被实机验证 —— 单测 (sync.test.ts T04) 全部 mock bridge, 而"模拟器在线即验证"欠账十版未还。旧时代运行 (CURRENT_STATUS §运行证据 `getAllCards=0`) 只覆盖了"RDB 为空"的恢复分支。

**连带影响评估**: 若嫌疑 (a) 成立, 则所有 async 桥方法的对象/数组返回值 (getAllCards / getRecentlyReviewedCards / getTodayReviewStats) 在实机上都不可用; 反向 web→native 对象传参 (upsertCard) 也需同场验证。

## 5. 排障方法论沉淀 (复用价值)

- `uitest dumpLayout` (非 uiDump) + `hdc file recv` 到工作区路径 (MSYS /tmp 对 Windows node 不可见) → node 解析 UI 树, 可定位 app 停留页面;
- **toast 抓现行**: 派发动作后 +0.8s dumpLayout (toast 3s), 双相位 (+0.8s/+2.5s) 可区分"静默降级"与"无 toast 路径";
- hilog 缓冲区约 73k 行/4min 即被 chromium 日志冲掉, 抓取窗口要短, 或先 `hilog -r` 再复现;
- hdc shell 透传的整行命令由设备端 /bin/sh 解析, 含 `&` 的参数必须加引号。

## 6. 修复过程 (2026-09-20 三轮收敛)

1. **web 侧防御归一化** (`parseBridgeRecords`, commit 905d95c): 兼容数组/JSON string — 复跑后诊断日志打脸: `rawType=number`, 嫌疑 (a)/(b) 均不是, 是第三种形态: **async JSProxy 回执路由整体失效**。
2. **原生序列化 JSON string** (getAllCards → `Promise<string>`): 复跑仍 `rawType=number`; CEF 日志 `CheckIsInJsPermission is_async:0/1` 双查; 补 `registerJavaScriptProxy` 后缺失的官方 `refresh()` 调用 — 仍 `rawType=number`。结论: 该 API 22 webview 的 async JSProxy 返回值通道不可用 (number 与载荷无关, 疑为内部消息 id), sync 方法 (notifyWebReady 等) 始终正常。
3. **切换推送通道 (最终方案)**: 放弃 web→native 拉取, 改用已实证可靠的 runJavaScript 派发通道 (native→web, FIFO 链即走它):
   - 原生: `notifyWebContentReady()` 后 `pushCardsToWeb()` — 读 RDB 全量 → `runJavaScript('window.__applyNativeCardRestore(<json>)')`, 全程兜底不抛;
   - Web: 模块加载时安装 `window.__applyNativeCardRestore(json)` — **store 非空不覆盖** (R-1 语义不变), 转换应用后 publish `memory:cards-updated`;
   - 纯 Web 环境该 handler 永不触发, 零影响; 拉取路径保留 (A4 断言 + 启动门 settle)。
