## 1. 一句话结论

两个未归因数字**全部清零**：Wave 1 的 **+133,600 B** 与 v1.6.2 轮的 **~122 KB** 欠账，共同根因是**同一笔构建会话差异** —— 记录 v1.6.2 产物时 `ets/sourceMaps.map`（129,676 B）未进包，而与之对比的产物都含该文件。剔除该会话差异后，同一环境重建口径下的**真实源码级增量**是：Wave 1 **+15,270 B**（≈0.33%）、v1.6.2 轮 **−120,062 B**（与预测 −122.2 KB 吻合到 1.8 KB）。归因落到具体条目，无剩余未解释字节。

## 2. 方法与口径

### 2.1 为什么必须「同环境重建」再比

HAP 是 zip，体积由「源码 + 构建环境」共同决定。历史产物已不在仓库（仅当前工作树的 HAP 存在，无 v1.6.0/v1.6.1/v1.6.2 tag），故按 SPEC §3 S3 的预案 **checkout 对应提交重建**：

| 版本 | 提交 | 用途 |
|---|---|---|
| v1.6.0 | `f26f613` | 122 KB 欠账基线 |
| v1.6.2 | `d247f9d` | 两笔欠账的共同基线 |
| Wave 1 | `73a94ab` | +133,600 欠账基线 |

三个 worktree 通过 junction 复用当前 `node_modules` / `harmony/oh_modules`，**故三者共享同一套工具链** —— 这正是能把「源码变化」与「工具链变化」分离的前提。

### 2.2 归因口径的三个必要修正

1. **剥离 Vite 内容 hash**：`HomePage-CmIJDChR.js` 与 `HomePage-DF6kqnqI.js` 是同一模块。不归一化会把「同模块内容变化」误判成「删旧增新」，产生成对的大额假差异。
2. **hash 判定要求含大写或数字**：否则 `course-cover-en` 会被 `cover-en`（恰好 8 位纯小写）误剥成 `course`，把中/德两套封面合并成一条。
3. **碰撞回退**：两个 chunk 归一后同名（如 `evaluateAnswer-*`）时必须回退原名各自比对，否则只保留其一、报出 ±35,808 这类假读数。

三条修正均有单测覆盖（T02/T04 为反向用例）。

### 2.3 确定性验证

同一 worktree 连续两次 `build:harmony:hap`（第二次为热缓存）产出 **逐字节相同的 HAP**（4,646,316 B，101 条目，含 `ets/sourceMaps.map` 129,676 B）。故本环境下构建是确定性的，归因结果可复现。

## 4. 欠账根因：`ets/sourceMaps.map` 的构建会话差异

### 4.1 定位过程

按 native / rawfile 拆分两份 v1.6.2 产物（记录值来自 `v1.6.2-EXAMPLE-LAYER-REPORT.md` §3.4 的分项）：

| 侧 | 记录 v1.6.2 | 重建 v1.6.2 | 差 |
|---|---|---|---|
| rawfile | 3,489,280 | 3,489,906 | +626 |
| native | 1,009,152 | 1,138,924 | **+129,772** |

**rawfile 侧吻合到 626 B，全部 130 KB 差异落在 native 侧。** 逐条列出 native 条目后：

- `icon.png` 359,333、`foreground.png` 374,662、`modules.abc` 214,724、`widgets.abc` 32,028 —— **与记录分项（350.9 / 365.9 / 209.7 / 31.3 KB）逐条吻合**；
- 记录分项「其余 27.7 KB」对应重建的「其余减去 `ets/sourceMaps.map`」= 28,501 B = 27.8 KB —— **吻合**；
- 即：**记录 v1.6.2 的 native 侧不含 `ets/sourceMaps.map`（129,676 B），重建必含。**

验证闭合：`4,515,968 + 129,676 = 4,645,644`，与重建 4,646,316 只差 672 B（与 v1.6.0 的 697 B 同量级，属构建噪声）。

### 4.2 为什么记录会话会缺该文件（推断，已标注）

`git diff f26f613 d247f9d --stat` 显示 **v1.6.0 → v1.6.2 未改动任何 ArkTS 文件**（`harmony/entry/src/main/ets` 差集为空，仅 `AppScope/app.json5`、`entry/oh-package.json5`、`CURRENT_STATUS.md` 变动）。`assemble-harmony-hap.mjs` 与 `build-profile.json5` 在该区间亦逐字未变。

**最可能的解释**：记录 v1.6.2 的会话里 ArkTS 源码自 v1.6.0 起未变，`CompileArkTS` 增量命中，`ets/sourceMaps.map` 未重新进包；而三个 worktree 均为干净编译，必然产出该文件。该解释与全部实测一致，但**未经原会话复现证实**，故标注为推断，不作为已证结论。

## 5. 归因 A — Wave 1（`73a94ab`）真实源码级增量

基线：重建 v1.6.2（4,628,830）→ 重建 Wave 1（4,644,100）。**总差异 +15,270 B。**

| 条目 | delta B | 说明 |
|---|---|---|
| `resources/rawfile/dist/harmony-chunk-graph.json` | **+10,664** | 新增：M5 引入的 chunk 依赖邻接表 sidecar（Vite 插件导出） |
| `ets/modules.abc` | +2,520 | ArkTS 编译产物（桥接层收敛/死代码清除） |
| `ets/sourceMaps.map` | +1,344 | 同上，随 ArkTS 产物 |
| `ets/widgets.abc` | +768 | 卡片文案/尺寸抽取（`CardTextFormatter` / `CardFormDimension`） |
| `ets/widget/component_collection.json` | +62 | 随组件清单 |
| `.../assets/useMemoryStore.js` | −88 | 代码分割重排 |
| **合计** | **+15,270** | |

**记录 +133,600 B 的分解**（file 口径，全部有据）：

```
+133,600  =  +15,440  真实源码级（重建口径，file）
           + 129,676  v1.6.2 记录产物缺 ets/sourceMaps.map
           +     672  v1.6.2 侧构建噪声（与 v1.6.0 的 697 B 同量级）
           -  12,188  Wave 1 侧构建噪声（0.26%）
```

即：**记录口径把「基线产物缺一个 source map」这一会话差异（≈129.7 KB）当成了增量**。剔除后，Wave 1 的真实源码级增量是 **+15,270 B（+0.33%）**，其中 70% 来自新增的 `harmony-chunk-graph.json` sidecar。

## 6. 归因 B — v1.6.2 轮 ~122 KB 欠账

基线：重建 v1.6.0（4,748,892）→ 重建 v1.6.2（4,628,830）。**总差异 −120,062 B。**

| 组 | delta B | 条目 |
|---|---|---|
| **v1.6.1 位图优化** | **−603,551** | `paper-texture-dark` −144,701、`paper-texture-warm` −148,733、`ink-splash-terracotta` −148,614、`icon-512.png` −140,318、`icon-192.png` −21,185（jpg → webp / 图标降采样） |
| **v1.6.2 英语例句层** | **+478,045** | `a1` +117,458、`a2` +100,673、`b1` +93,930、`b2` +165,984 |
| **其他（代码分割重排）** | **+5,444** | `radix-ui.js` −58,430 与 `react-vendor.js` +11,326（manualChunks 调整）、`ReadingSessionPage.js` +47,268、`useCourseStore` 拆分（−15,888 / +3,833）、`courses` +12,111、`passages` +72、`index.js` +3,016 等 |
| **合计** | **−120,062** | |

与 v1.6.2 报告的预测净额 **−122.2 KB** 吻合到 **1.8 KB（0.1%）**。位图 −603,551 B 与文档记载的 **−589.4 KB** 属同量级（口径边界差异，见 §8）。

**记录 −249,171 B 的分解**：

```
-249,171  =  -120,062  真实源码级（重建口径）
           - 129,676  v1.6.2 记录产物缺 ets/sourceMaps.map
           +     672  v1.6.2 侧构建噪声
           +      -?   —— 见下
```

精确闭合：`-249,171 = -120,062 - 129,676 + 567`。即记录值比「真实源码级 + source map 会话差异」**还小 567 B**，该 567 B 为构建噪声。**欠账 = 被误计入的 `ets/sourceMaps.map`（129,676 B）**，不是任何未识别的源码体积。

## 8. 口径边界与诚实声明

1. **位图口径差异**：本报告测得 v1.6.1 位图项 **−603,551 B**，文档记载 **−589.4 KB**。二者差 14 KB，源于归类边界不同（本报告含 `icon-192/512.png` 与 webp 新增的净额；文档可能只计三张背景纹理）。**不改写文档原值，以本节标注差异。**
2. **重建噪声**：Wave 1 侧重建比记录大 12,188 B（0.26%），v1.6.0 侧仅 697 B。前者未能进一步拆到条目（记录产物已不在），按「重建-记录噪声」如实列示，不伪装成已归因的源码项。
3. **根因 §4.2 为推断**：`sourceMaps.map` 缺失与「ArkTS 增量编译」的因果链与全部实测一致，但未在原会话复现，标注为推断。
4. **本报告不改动任何历史数字**：记录值原样保留并标注口径，差异在 §5/§6/§8 说明。

## 10. 结论对账

| 项 | 记录口径 | 真实源码级（同环境重建） | 差额根因 |
|---|---|---|---|
| Wave 1 HAP 增量 | +133,600 B | **+15,270 B** | `ets/sourceMaps.map` 会话差异 129,676 B + 构建噪声 |

**两个未归因数字 = 0。** 所有差异均已落到条目、或已定性为已测量的构建噪声（≤0.26%）或已定位的构建会话差异（129,676 B）。
