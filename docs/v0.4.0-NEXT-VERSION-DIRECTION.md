# Next Version Direction — Wordaydream v0.4.0-harmony

## 概述

Wordaydream 鸿蒙移动版 v0.3.0-harmony 已完成全部 5 个 Stage 的迭代，5/5 PASS，974/974 tests 通过，贝叶斯后验概率达到 0.85。v0.3.0-harmony 在 D1 TTS 双路径（@ohos.textToSpeech Kit 原生 + Web SpeechSynthesis fallback）、D3 ArkWeb 性能优化（Vite manualChunks 4 chunk + Brotli/Gzip 双压缩 + IndexedDB 索引 + 鸿蒙 relationalStore 索引）两大方向上完成了关键交付，rawfile/dist 体积压缩至 .br 0.262MB（压缩率 87.7%），并在 RELEASE_CHECKLIST 中沉淀了 11 项真机验证项与 5 项性能基线。

v0.4.0-harmony 的候选方向基于三条信息源汇聚：(1) v0.3.0-harmony 5 项反思记录中暴露的工程不确定性（如 voiceschanged 真机触发风险、vite-plugin-compression 兼容性、IndexedDB 迁移风险）；(2) v0.2.0-harmony NEXT-VERSION-DIRECTION 中延后的 D2/D4 方向（离线 LLM 推理 + 多设备适配）；(3) v0.3.0-harmony 11 项真机验证与 5 项性能基线预期反馈（由用户在 DevEco Studio 内执行后回填）。本文档为 P-Light 级别方向研究，由 bayesian-planner Phase 5.5 Hook 自动触发，未进行外部 webfetch 研究；当 v0.4.0-harmony 正式启动迭代时，应在 Phase 2 中执行完整 Code Mine 与 Paper Radar。

## 候选方向

### D1: 离线 LLM 推理（D2 兑现）

D1 兑现 v0.2.0-harmony NEXT-VERSION-DIRECTION 中延后的 D2 方向。技术路径为 ONNX Runtime Mobile + 量化模型，候选模型 TinyLlama-1.1B-Chat-v1.0 Q4 量化（模型大小约 600MB，目标推理延迟 P95 < 3s 在主流鸿蒙设备上）。核心权衡为模型大小 vs 推理延迟 vs 词汇学习场景适配度：1.1B 参数模型在词汇解释、例句生成上能力有限，但作为离线 fallback 可接受。v0.3.0-harmony 已完成 ArkWeb 性能优化（Brotli 压缩 + IndexedDB 索引），为离线 LLM 推理提供了基础性能保障。优先级 P1，confidence 0.55。confidence 偏低的原因：(1) 鸿蒙 ONNX Runtime Mobile 的 GPU delegate 支持情况不明；(2) 600MB 模型包对安装包体积影响显著（v0.3.0-harmony rawfile/dist originals 2.137MB，模型将使包体积增加 280 倍）；(3) 词汇学习场景对延迟敏感（用户期望 < 1s 响应），3s P95 可能不可接受。建议在 Phase 2 Paper Radar 中重点调研移动端 LLM 量化论文（GPTQ / AWQ / SmoothQuant）。

### D2: 多设备适配（D4 兑现）

D2 兑现 v0.2.0-harmony NEXT-VERSION-DIRECTION 中延后的 D4 方向。覆盖 tablet（10.1 寸 / 12 寸）与 2in1 大屏布局，采用 ArkUI GridContainer + 响应式断点（sm 320-600dp / md 600-840dp / lg 840dp+）。对 formBindingData.getDimension API 采用防御性写法（try-catch + 默认值 fallback + 单元测试覆盖异常分支），消除 v0.2.0-harmony Stage 4 中遗留的 API 不确定性。v0.3.0-harmony 已完成 TTS 双路径与性能优化，为多设备适配提供了稳定基础。优先级 P1，confidence 0.65。confidence 受限原因：本机无 tablet/2in1 真机，多设备适配验证依赖用户在 DevEco 内的 emulator + 真机回填。

### D3: TTS 真机验证兑现

D3 为 v0.4.0-harmony 的 P0 阻塞方向。用户在 DevEco Studio 内执行 v0.3.0-harmony RELEASE_CHECKLIST 中的 11 项真机验证项（含 @ohos.textToSpeech Kit 引擎可用性、speak 方法签名、de-DE 离线 voice、Web SpeechSynthesis voiceschanged 触发、chunk splitting 超时、朗读按钮条件、rate 四档选择器、ArkWeb Brotli 解码、rawfile/dist 体积对比、Lighthouse 分数、relationalStore 索引创建）与 5 项性能基线（rawfile 体积、首屏加载、manualChunks 顺序、TTS speak 延迟、IndexedDB 查询延迟）。回填数据后触发 v0.4.0-harmony 范围调整：(1) 若 TTS 真机验证失败（如 de-DE voice 不可用），启动 hotfix v0.3.1-harmony 修复 TTS fallback 逻辑；(2) 若性能基线未达预期（如首屏 > 2s），D4 优先级提升至 P0；(3) 若 Brotli 解码不支持，回退到 gzip-only 模式。优先级 P0 阻塞，confidence 0.90。confidence 最高原因：D3 为执行性任务，无技术不确定性，仅依赖用户时间投入。

### D4: ArkWeb 性能深度优化

D4 在 v0.3.0-harmony D3 基础上进一步优化 ArkWeb 性能。优化路径三线并行：(1) 资源预加载（rel="modulepreload" 提前加载 manualChunks 4 chunk，减少首屏 JS 解析时间）；(2) Service Worker 缓存（缓存静态资源 + IndexedDB 数据快照，离线场景下秒开）；(3) Web Worker 解析并行化（将 papaparse CSV 解析 + jsonrepair + zod 校验移至 Web Worker，避免阻塞主线程渲染）。目标首屏 < 1.5s（v0.3.0-harmony 基线需 D3 真机回填后对比），Lighthouse Performance > 90。优先级 P2，confidence 0.70。confidence 受限原因：Service Worker 在 ArkWeb 的注册行为不确定，需 Phase 2 调研 ArkWeb M114 的 SW 支持情况。

### D5: relationalStore 查询优化

D5 在 v0.3.0-harmony Stage 4 的 3 索引基础上进一步优化鸿蒙 relationalStore 查询性能。优化路径三线并行：(1) 复合索引（CREATE INDEX idx_due_last_review ON memory_cards(due, lastReviewAt)，覆盖 getRecentlyReviewedCards 查询）；(2) 分页查询（LIMIT + OFFSET 替代 getAllCards 全表返回，避免大数据量内存峰值）；(3) 查询计划分析（EXPLAIN QUERY PLAN 验证索引使用情况，避免全表扫描）。目标 getAllCards 1000 张延迟 < 200ms（v0.3.0-harmony 基线需 D3 真机回填后对比）。优先级 P2，confidence 0.75。confidence 较高原因：复合索引与分页查询为成熟 SQL 优化实践，relationalStore 兼容 SQLite 语法。

- **Stage 3: D4 ArkWeb 性能深度优化**（modulepreload + Service Worker + Web Worker）。subagent 实施 Vite build 配置调整与 Service Worker 注册，目标首屏 < 1.5s。性能对比 v0.3.0-harmony 基线（由 Stage 1 回填数据提供）。
